# План: один рабочий слот и очередь задач (пилот на reels-radar)

Дата: 2026-10-25. Статус: черновик, ждёт одобрения Некита.

## Зачем
Ноут 8 ГБ. Сторож 25.10 снимал ботов 72 раза, 24.10 19 раз. Слушатели Telegram весят 5-130 МБ,
ноут кладёт тяжёлая работа (claude -p ~280 МБ, Whisper, эмбеддер ~450 МБ, Chromium проверки профилей),
а сторож гасит слушателя целиком, и бот перестаёт отвечать.

Правило новой схемы: слушают все, работает один.

```
 СЛУШАТЕЛИ (всегда живы)          ОЧЕРЕДЬ                  СЛОТ (один)
 reels-bot, idea, dungeon ...  ->  P0 ты в Claude Code  ->  тяжёлое по одному
                                   P1 по расписанию        claude -p / Whisper /
                                   P2 фон, хвосты          Chromium / эмбеддер
                        флаг yield: задача доделывает элемент, сохраняет место, выходит
 СТОРОЖ: сначала yield слота, слушателей гасит в последнюю очередь
```

## Решения Некита (25.10)
1. «Вне очереди» = работа в Claude Code. Кнопки ботов отдельно не считаются.
2. Пока Некит работает, лёгкое может идти, тяжёлое по объёму свободной памяти.
3. Порядок фона: харвестер-ночь > рилсы-ночь > проверка профилей > аудит > бэкфиллы.
4. Жёсткие часы только у dungeon-tasks (вопросы) и доставок (дайджест вс 19:00, friday-review пт 18:00). Они в слот не идут.
5. Не успели за сутки: light-режим (у reels-radar он уже есть: light_below_gb), хвост на следующие сутки.
6. Проверка профилей Instagram идёт в очередь автоматически, в пределах verify_daily_budget.
7. Начинаем с пилота на reels-radar, потом переносим по одному проекту.

## Пилот: что делаем

### Шаг 1. tools/slot (общий, маленький, на Python без зависимостей)
- `slot.py run <job> [--class heavy|light] -- <cmd...>`: берёт блокировку слота (fcntl, файл state/slot.lock),
  пишет state/current.json (job, pid, класс, старт), запускает команду, снимает блокировку.
  Слот занят: выход с кодом 75 и записью в лог, без ожидания.
- `slot.py yield` / `slot.py unyield`: ставит и снимает state/yield.
- `slot.py tick`: раз в 5 минут из launchd. Читает jobs.yaml (job, команда, класс, приоритет, частота daily/weekly),
  state/last_run.json и решает, что запускать: самый приоритетный просроченный job, который разрешён сейчас (см. шаг 2).
- `slot.py status`: что идёт, что в очереди, когда что последний раз отработало.
- Лог: tools/slot/slot.log (подхватит log-rotate).

### Шаг 2. Когда тяжёлое разрешено
- «Некит работает»: хук Claude Code (UserPromptSubmit) пишет время в tools/slot/state/interactive.
  10 минут после последнего промпта считаются работой.
- Во время работы: light-задачи идут, heavy только если pressure норма И swap < 4000 МБ (пороги в jobs.yaml).
  Иначе slot.py ставит yield, текущая heavy-задача выходит после элемента.
- Без работы: heavy идёт, если сторож на уровне 0.

### Шаг 3. reels-radar умеет уступать
- `run` (live.py/pipeline): проверка state/yield между рилсами. Есть флаг: выход с 0, необработанные остаются `new`.
- `sources verify` (sources/verify.py, цикл verify_batch): проверка флага между профилями, выход с `stopped: YIELD`.
- Тесты: оба цикла останавливаются по флагу после текущего элемента, состояние не теряется.

### Шаг 4. Перевод расписания reels-radar в очередь
- jobs.yaml: `reels-night` (heavy, P1, daily, `run --limit 60`), `reels-verify` (heavy, P1 ниже рилсов, daily, бюджет 120).
- plist reels-radar-night: снять StartCalendarInterval (bootout, бэкап в launchd/), запуск только через slot.
- reels-radar-digest остаётся по часам (вс 19:00), это доставка, light.
- Бот reels-radar-bot не трогаем: он слушатель.

### Шаг 5. Сторож
- Уровень 1: сначала `slot.py yield` и ждать 2 проверки. Слушателей TIER1 снимать, только если не помогло.
- reels-radar-bot перенести из TIER1 в последнюю очередь (снимается только на уровне 2).
- Временная правка RESUME_ORDER от 25.10 откатывается (бэкап resource-guard.sh.bak-1025).
- Новые задачи слота добавить в NIGHT-замер сторожа (строки NIGHT в логе).
- CAPS не меняются, сумма остаётся в TOTAL_CAP_MB.

## Проверка
- Тесты slot.py: блокировка (второй run получает 75), выбор следующего job, yield, interactive-окно. Тесты reels-radar: остановка по yield.
- Живьём: tick запускает reels-verify на 3 профиля. Промпт в Claude Code во время прогона: при swap выше порога задача
  выходит после текущего профиля (в логе YIELD), после 10 минут тишины tick продолжает с того же места.
- Сутки наблюдения: reels-night и reels-verify отработали без ручного запуска, SHED reels-radar-bot в логе сторожа 0,
  общее число SHED ниже 72/сутки (сравнение по resource-guard.log).

## Не в пилоте
- tg-harvester (night, audit), idea-bot, dungeon-tasks, friday-review, бэкфиллы: переносим после пилота по одному.
- Бесплатный LLM-запас и общий раннер claude -p (отдельный план).

## Риски
- Хук UserPromptSubmit добавляется в глобальные настройки Claude Code: каждый промпт пишет файл. Дёшево, но правка общих настроек.
- Сессия Instagram: verify уходит между профилями, а не заморозкой, Chromium закрывается штатно.
- Mac спал: tick после пробуждения запустит просроченное по одному, а не всё сразу.
